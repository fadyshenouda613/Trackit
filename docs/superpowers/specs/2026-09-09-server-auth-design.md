# Server and account sign-in — design

Date: 2026-09-09. Branch: `feat/server-auth`.

## What this is

Two halves of one feature. `apps/server` grows from a scaffold into a real
Express + PostgreSQL service with a Drizzle schema that mirrors the desktop's
SQLite tables, and an auth API. The desktop's sign-in and sign-up cards stop
accepting `admin / admin` and call that API, keeping the refresh token
encrypted on disk so a session survives as long as the freelancer is offline.

Nothing about the local data path changes. A token that has expired blocks
sync and nothing else; the app opens, reads and writes without an account at
all. Sync itself is not built here — the sync engine is the next piece and
this is what it will authenticate with.

## Shared package

`packages/shared/src/schemas/auth.ts` defines, once, every shape that crosses
the network or the bridge for auth:

| Schema | Fields | Used by |
|---|---|---|
| `registerInputSchema` | `name`, `email`, `password` | `POST /auth/register`, bridge `auth.register` |
| `loginInputSchema` | `email`, `password` | `POST /auth/login`, bridge `auth.login` |
| `refreshInputSchema` | `refreshToken` | `POST /auth/refresh` |
| `logoutInputSchema` | `refreshToken` | `POST /auth/logout` |
| `authUserSchema` | `id`, `email`, `name`, `createdAt` | responses, bridge status |
| `authTokensSchema` | `accessToken`, `accessExpiresAt`, `refreshToken`, `refreshExpiresAt` | responses |
| `authSessionSchema` | `user`, `tokens` | register/login/refresh responses |
| `authStatusSchema` | `{ state: 'signedOut' }` or `{ state: 'signedIn', user, session: 'active' \| 'expired' }` | bridge `auth.status` |

Email is trimmed and lower-cased by the schema, so the server never stores two
spellings of one address. `PASSWORD_MIN_LENGTH` (8) lives beside the password
schema and the sign-up card reads it from there.

`ApiErrorCode` in `api.ts` gains four codes the account calls need:
`unauthorized` (wrong email or password, or a session the server no longer
honours), `conflict` (the email is taken), `offline` (the server could not be
reached) and `rate_limited`.

## Server

Express 5, TypeScript, Drizzle over `pg`. Runs from source with `tsx` in
development; bundled with esbuild to `dist/index.js` for the container (only
`@trackit/shared` is bundled in, every dependency stays a runtime import).

### Schema (`src/db/schema.ts`)

- `users`: `id` (uuid, minted by the server at register — the client-minted
  id rule is about syncable rows, and an account is the server's own),
  `email` (unique, lower-cased), `name`, `passwordHash` (argon2id),
  `createdAt`, `updatedAt`.
- `refreshTokens`: `id`, `userId`, `familyId`, `tokenHash` (sha256 of the raw
  token, unique), `expiresAt`, `createdAt`, `revokedAt`, `replacedById`.
- The ten syncable tables — `clients`, `projects`, `milestones`,
  `checklist_items`, `notes`, `time_entries`, `invoices`, `invoice_lines`,
  `payments`, `settings` — with the SQLite columns typed for Postgres
  (`timestamptz`, `boolean`, `double precision`, `integer` cents), plus on
  every one: `user_id` (uuid, not null, references users) and `server_seq`
  (`bigserial`, indexed together with `user_id`). `sync_state` is not there:
  it is a local column. `settings` is one row per user, keyed by `user_id`.

Migrations are generated by drizzle-kit into `apps/server/drizzle/` and
applied at startup and in tests with Drizzle's migrator. Never edited; the
next one is written.

### Auth (`src/auth/`)

Plain functions that take a `db` handle, the way the desktop's repositories
do, so they test without Express.

- **register**: hash with argon2id, insert, issue a session. A duplicate email
  is `409 conflict`.
- **login**: look the user up, verify. An unknown email verifies against a
  fixed dummy hash so the two failures take the same time. Both are
  `401 unauthorized` with the same message.
- **refresh**: hash the presented token and find it. Unknown → 401. Already
  rotated (`replacedById` set) or revoked → this is a reuse: revoke every
  token in the family, then 401. Expired → 401. Otherwise insert the
  successor in the same family, mark the old one replaced, and answer with a
  fresh pair.
- **logout**: revoke the family the token belongs to. Always 204.
- **me**: `GET /auth/me` with a bearer access token, for the desktop to
  confirm a session and for the tests.

Access tokens are HS256 JWTs (`jose`), 15 minutes, `sub` = user id, `sid` =
token family. Refresh tokens are 32 random bytes, base64url, 90 days,
extended on every rotation — which is what lets a session outlive a long
offline stretch: the app only needs to reach the server once every 90 days.

### Hardening

- `helmet()` defaults.
- `cors` with an explicit allowlist from `CORS_ORIGINS`; empty means no
  cross-origin caller is allowed. The desktop calls from the main process
  with no `Origin`, so it is unaffected.
- `express-rate-limit` on `/auth/register`, `/auth/login` and
  `/auth/refresh`, per IP, limits from env so the tests can drive them low.
- One error handler. Every failure is `{ error: { code, message } }`;
  validation failures add `details`. In production a 500 says only
  "Something went wrong"; the stack goes to the log, never the wire.
- `trust proxy` is on when `TRUST_PROXY=1`, which Railway and Render need for
  the rate limiter to see the real address.
- `GET /health` answers without touching the database; `GET /health/ready`
  runs `select 1`.

### Tests

`*.integration.test.ts` under `apps/server/src` run with supertest against
the app and a real Postgres from `apps/server/docker-compose.yml`
(`postgres:16`, port 5433). Root `npm test` excludes them; `npm run
test:integration -w @trackit/server` runs them. They cover register, login,
refresh rotation, reuse detection revoking the family, logout, `me`, the
error shape, and the rate limit.

CI gains a `server` job with a Postgres service container that runs the
integration tests and the production bundle, beside the existing typecheck
and test job.

### Deploying

`apps/server/Dockerfile` builds from the repository root (npm workspaces need
the root lockfile). `railway.json` and `render.yaml` at the root point at it
with `/health` as the health check. `apps/server/.env.example` lists every
variable with a comment.

## Desktop

### Main process (`src/main/auth/`)

- `session-store.ts`: reads and writes `session.json` in `userData`:
  `{ version: 1, user, refreshToken, refreshExpiresAt, encrypted }`. The
  refresh token is `safeStorage.encryptString`'d and base64'd. Where the OS
  offers no encryption (some Linux sessions) it is stored plain with
  `encrypted: false` and a warning in the log, because a session that never
  survives a restart breaks the app's central promise. The store takes its
  cipher as an argument so it tests without Electron.
- `client.ts`: `fetch` against `TRACKIT_SERVER_URL` (env, falling back to
  `MAIN_VITE_SERVER_URL` from a `.env` at build time, then
  `http://127.0.0.1:4000`). Maps HTTP failures to `ApiErrorCode`: a network
  failure is `offline`, 401 `unauthorized`, 409 `conflict`, 429
  `rate_limited`, anything else `internal`.
- `service.ts`: `createAuthService(deps)`. Holds the status and the access
  token in memory. `login`/`register` store the session and push
  `auth:changed`. `logout` tells the server (best effort) and clears the
  file. `accessToken()` returns a live token, refreshing through the store
  when it is within a minute of expiry; a network failure leaves the
  session `active` and answers `offline`; a 401 marks it `expired` and
  pushes the change. At launch a stored session is `active` on trust and a
  background refresh confirms it.

### Bridge

`LedgerApi.auth`: `status`, `register`, `login`, `logout`, `onChanged`. One
handler each in `auth-ipc.ts`, thin, validated with the shared schemas.

### Renderer

- `data/use-auth.ts`: `useAuthStatus` (query, kept current by `onChanged`),
  `useLogin`, `useRegister`, `useLogout`.
- `auth-session.ts` loses the stand-in and the localStorage session; it keeps
  the once-per-machine welcome flag.
- `AuthScreen`: the cards submit asynchronously, show "Signing in…" on the
  button, and state the refusal beneath the field in the same grey prose:
  wrong pair, taken email, no connection, too many attempts, or the server's
  own message. The sign-in note no longer mentions `admin`.
- `App.tsx`: the gate reads `useAuthStatus`. Until it answers, the window
  shows only its chrome. Signed out → sign-in (or offline with no link).
  Signed in → the app, whatever the token state. `authView` remains plain
  React state so the States panel's Account axis (In, Sign in, Sign up,
  Welcome, Offline) forces any card, or the app, regardless of the real
  session — exactly as before.
- `SettingsAccount`: states the session (`Signed in`, or `Session expired —
  sign in again to sync; your work here is unaffected`) and disables Sync
  now while it is expired.

## Out of scope

The sync engine, the desktop's real sync state (the footer still reads the
fixtures), and password reset.
